# dsh-web-search 验证功能地图

本目录是本仓库用户可见行为的验证事实源，按用户视角写：功能是什么、怎么走到它、怎么驱动它、什么可观察的终态证明它好使。

跑之前先读本文件，再读对应功能的文件。技能正文（[`../SKILL.md`](../SKILL.md)）讲怎么起实例、怎么用 ego、证据放哪；本目录讲要驱动哪些功能、每条旅程断言什么。

`docs/feature-map.md` 是从代码生成的功能面清单，讲这个插件有哪些面、各面的期望反馈。本目录是从用户视角写的验证旅程，讲每条旅程怎么跑、跑完什么样算过。两者不合并：本目录的旅程是本仓库验证的事实源。

## 基线前提

- 用 npm 装的 `dsh` 命令起隔离 web 实例，独立 DSH_HOME、独立 profile、独立端口。做法见 [`../SKILL.md`](../SKILL.md) 的 Launch。
- 实例起来以后先跑 Doctor。健康检查不是 200 且 `ok:true`，不往下驱动。
- ego 只连隔离实例的带 token URL，不碰桌面端实例，不碰 `~/.dsh/profiles/desktop`。
- 每次旅程从实例的默认状态起步；上一条旅程改过的设置，下一条要么复原要么在前提里说明。
- 真实网络调用按后端计预算。每个后端一次验收最多 3 次真实调用。

## 驱动约定

- 优先用可访问名和稳定的 DOM 结构，不用坐标和 tab 顺序。
- 页面上的动作算一步，页面状态的变化算一步，两步都要留证据。
- 每个动作前截一张图，动作后截一张图。只截终态证明不了动作真的生效。
- 命令逐字照抄，不改引号和参数。
- 收尾只清实例和临时状态，不清证据。

## 证明与跳过怎么报

- 证明里贴原始输出，不写「通过」。
- 截图要能认出是哪个实例、哪个功能。
- 记下用的功能 ID 和入口路径。
- 走不通的路径，报告试过的命令和没满足的前提，别把「从别的路径验过」写成「这条验过」。
- 没真跑过的功能，在对应文件的 Gotchas 里写明「本轮未跑」和为什么。

## 功能条目约定

每个功能文件一个 H1 标题加一段描述用户可见行为的话，然后是四个二级标题，顺序固定：

1. `Sub-features`：短 ID，每个行为一行。
2. `How to get to it (user POV)`：用户从哪儿进。
3. `Driving it with ego`：先写 `Preconditions:`，再用带标签的条目把每个用户动作和确切命令、可观察结果配成对。
4. `Gotchas`：会浪费或作废一次验收的坑。

实现细节不进地图。只写用户路径、稳定的入口、必需状态、命令和可观察的证明。

## 功能

- [web_search 搜索](./web-search.md)：模型调 `web_search` 拿多来源真实结果，中英文查询都验。
- [web_fetch 抓取](./web-fetch.md)：模型调 `web_fetch` 直连抓取单页正文。
- [设置页](./settings-page.md)：插件在宿主里的设置页，引擎配置、模式切换、保存、额度刷新。

## 驱动方式

三条驱动方式分别写进各功能的 Driving 一节，不单列成功能：

- **keyless**：免凭据，Keenable、AnySearch、GitHub 匿名可用。全自动，不需要人参与。
- **keyed**：带真实 provider key，走付费后端。key 的注入纪律见 [`../SKILL.md`](../SKILL.md) 的 keyed 一节。
- **dogfooding**：以 ego 当真实用户走全流日常，产出体验 finding，不做定向断言。
