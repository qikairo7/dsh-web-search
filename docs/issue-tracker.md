# Issue 与 PR 的约定

这个仓库用 GitHub 自带的 issue 和 PR，没有别的 tracker。用 `gh` 操作它们。动 issue 和 PR 之前先加载 `github-roles` 这个 skill，它说清了哪个账号做哪件事、每个账号对外能说什么。

## 标签

issue 和 PR 上的标签是中文的。下面是一些通用叫法和这个仓库标签的对照，读别的 skill 或别的项目的文档时按这张表换算：

| 通用叫法 | 这个仓库的标签 | 意思 |
|---|---|---|
| `bug` | bug | 确认的缺陷 |
| `enhancement` | 增强 | 新功能或体验改进 |
| `task` | 任务 | 有明确范围的实现或维护工作 |
| `needs-triage` | 待分诊 | 等分诊，新单的入口状态 |
| `needs-info` | 待补信息 | 信息不够，报告人补了再继续 |
| `ready-for-agent` | 可交代理 | 规格齐全，代理可以直接接 |
| `ready-for-human` | 需人工处理 | 要维护者决策或动手 |
| `wontfix` | 不予修复 | 确认不做，理由写在评论里 |

另有一个这个仓库自己的状态，别的叫法里没有对应：`待裁决`。它用在链跑到一半、有只有维护者能定的事时，和「需人工处理」的区别是「待裁决」卡的是这一条链，「需人工处理」说的是整张单要人做。

## 一张单怎么走

1. 新单带着 `待分诊` 进来。
2. 分诊把它判成三种之一：受理的挂 `可交代理`，写好规格；信息不够的挂 `待补信息`；不做的挂 `不予修复` 并关单。
3. `待补信息` 的单，报告人在单上回了话之后，分诊会自动重新判一次，回到第 2 步。
4. `可交代理` 的单，由实现接手，做完开 PR。

每张单同一时间只带一个状态标签。换状态时把旧的状态标签摘掉。

## 对外的说法

这个仓库的 issue 和 PR 上，评论不写在哪个工具里生成的声明。每个账号说话的口径见 `github-roles` skill。
