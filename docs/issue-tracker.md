# Issue 与 PR 的约定

这个仓库用 GitHub 自带的 issue 和 PR，没有别的 tracker。用 `gh` 操作它们。

仓库用三个账号分工：作者账号 qikairo-bot 开单、建分支、提交、开 PR 和回应评审；评审账号 qikairo-review 只做评审；维护者账号 qikairo7 做分诊、裁决、合并和发版。

## 标题与元数据

issue 和 PR 的标题一律全中文。具体的格式待定，见 #42。

开 issue 和开 PR 都要补齐元数据：议题类型、受理人、标签、里程碑；PR 另加评审者，开出来后立刻补。各字段具体填什么待定，见 #42。元数据不齐的 PR 评审会打回。

## 标签

标签用中文或通用的英文词，只标内容和结论，不表示处理状态。仓库现在有 9 个：

| 标签 | 用途 |
|---|---|
| bug | 确认的缺陷 |
| 增强 | 新功能或体验改进 |
| 任务 | 有明确范围的实现或维护工作 |
| 文档 | 文档的补充与修正 |
| 审计 | 审计发现的待处理问题 |
| 评审遗留 | 延期处理的评审发现 |
| 跟进 | 评审或审计衍生的跟进项，默认排下批 |
| 安全 | 安全相关，按安全策略私下报告处理 |
| 不予修复 | 确认不做，理由写在评论里 |

新单由模板带类型标签：Bug 报告带 `bug`，功能请求带 `增强`，问题咨询带 `任务`。审计和评审产生的单，发单账号按内容另加 `审计`、`文档`、`评审遗留` 或 `跟进`。

仓库没有 `待分诊`、`待补信息`、`可交代理`、`需人工处理`、`待裁决` 这五个状态标签。别的 skill 提到这些状态时，按 issue 的 open / closed 和评论里的结论处理，不要去找标签。

## 一张单怎么走

issue 用 open / closed 表示进度，不另设状态标签。

1. 新单带着类型标签进来。
2. 处理结论写在 issue 评论里。不做的单挂 `不予修复` 后关闭。
3. 要做的单开 PR，正文写 `Fixes #<单号>`；PR 合入后 issue 自动关闭。

## PR

main 受规则集保护：必须走 PR，`check` 通过。只允许 squash 合并，合并后自动删分支。合并时默认用 PR 标题当提交标题，合并的人可以改。

## 对外的说法

这个仓库的 issue 和 PR 上，评论不写在哪个工具里生成的声明。作者账号说改了什么、怎么验；评审账号给证据和结论；维护者账号说结论和下一步。
